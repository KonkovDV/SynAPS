Главное по смыслу:

1. **Независимый нотариус доверял штампам солвера** (A-02, A-03): проверка
   календарей брала `setup_minutes` и `aux_resource_ids` из ответа солвера.
   Солвер, занизивший переналадку или «забывший» ресурс, получал сертификат
   допустимости при фактическом нарушении календаря. Это нарушало инвариант
   проекта `FEASIBLE ⇒ proven_hard_violations = ∅` в его содержательном смысле.
2. **Целочисленное зерно времени было неустойчиво к IEEE-754** (A-01):
   `ceil(21 / 0.7) = 31`, потому что `21 / 0.7 = 30.000000000000004`. Ошибка
   была в Python, в Rust-ядре и в кабельном адаптере одновременно.
3. **CP-SAT молча обнулял дробные веса и принимал отрицательные** (A-04);
   отрицательный вес ломает лексикографическую big-M-декомпозицию и
   двойственную оценку `floor(B / S_B)`.
4. **BHK-оценка переналадок была заявлена валидной «на любой матрице»**
   (A-06) — это неверно для неметрических матриц с повторяющимися состояниями;
   исправлено метрическим замыканием (Флойд–Уоршелл), на метрических матрицах
   результат не меняется.
5. **Генераторы «сидовых» инстансов не воспроизводимы** (A-13): `uuid4()`
   давал новые ID при каждом вызове, а солверы разрывают ничьи по `str(id)`.
6. **Релизные нативные колёса непереносимы** (R-10, найдено Red Team и
   воспроизведено в среде аудита): `target-cpu=native` из `.cargo/config.toml`
   попадал в релизную сборку; на другом CPU импорт `synaps_native`
   завершается SIGILL, который Python-fallback перехватить не может.

## 1. Методика

* **Алгебра.** Для каждой формулы (зерно времени, целевая функция и её

  против исходного дерева).
* **Red Team.** Ревью итогового диффа, поиск путей, не покрытых golden и
  тестами, повторная проверка честности evidence и заявлений.
* **SOTA.** Поиск литературы 2024–2026 (раздел 8, ссылки на источники).
* **Ограничения.** `npm ci` для control-plane в этой среде запрещён
  политикой — control-plane проверен статически. Бенчмарки 50k+ операций не
  перезапускались: эталонные (hashed) числа не трогались.

## 3. Дефекты алгебры (A-01…A-13)

### A-01. Целочисленное зерно времени

Контракт: резерв `k = max(1, ⌈b / v⌉)` минут, где `b` — базовая длительность,
`v` — скорость станка; нотариус требует `span + ε ≥ b / v`. В IEEE-754 частное
не точное: `21 / 0.7 = 30.000000000000004`, `⌈·⌉ = 31`. Исправление:
`k = max(1, ⌈b / v − ε⌉)`, `ε = GRAIN_EPSILON_MIN = 10⁻⁹` мин — тот же допуск,
что у нотариуса, поэтому согласованность выполняется по построению:
`k ≥ b / v − ε ⇔ ¬(k + ε < b / v)`. Оценка: относительная ошибка частного
`≤ 2⁻⁵²` (округление `v` и деления), т.е. `ε` доминирует при `b / v < ~4·10⁶`
мин. Исправлено в `synaps/timegrain.py` (`ceil_minutes`), Rust
`list_schedule.rs` и `synaps/domains/cable/adapter.py`; нативный ALNS-путь
уже пересчитывал длительность через `duration_minutes_for`.

### A-02 / A-03. Нотариус доверял штампам солвера

`_check_work_center_calendar` строил окно занятости `[start − setup, end]` по
`assignment.setup_minutes`, а `_check_aux_calendar` перебирал только
`assignment.aux_resource_ids`. Солвер, занизивший переналадку, сдвигал её в
закрытый период календаря; солвер без штампа ресурса пропускал проверку
календаря ресурса целиком (пул-свип TimeTable при этом использовал требования
задачи — несогласованность внутри нотариуса). Исправление: окно — более
длинное из штампа и переналадки, выведенной нотариусом из последовательности
станка / линии; удерживаемые ресурсы — требования задачи (с привязкой к
выбранному режиму) ∪ штамп.

### A-04 / A-05 / A-10. Численная гигиена CP-SAT

Иерархическая цель `f = C_max · S_B + Σ c_k F_k`, `S_B = 1 + Σ c_k U_k`
(`U_k` — верхняя граница `F_k`), даёт лексикографический порядок при
`0 ≤ Σ c_k F_k < S_B` и двойственную оценку `C_max ≥ ⌊B / S_B⌋`. Раньше
`c_k = int(w_k)`: `{"setup": 0.5}` давал `c = 0` (кабельный домен обходил это
через `round(w · 100)`); отрицательный `w_k` нарушает `0 ≤ Σ c_k F_k` и делает
и порядок, и оценку неверными. Теперь `c_k = round(K · w_k)` для наименьшего
`K ∈ {1, 10, …, 10⁶}`, делающего все веса целыми; целые веса дают `K = 1`
(модель бит-в-бит прежняя); отрицательные / NaN — `ValueError`. A-05:
`floor` вместо `int()` для due-offset (`int(−2.5) = −2`, а нужно `−3`).
A-10: `time_limit_s` передаётся в CP-SAT как `float` (раньше `0.5 → 0`).

### A-06. BHK-оценка переналадок

Последовательность на станке — **маршрут** по мультимножеству состояний
(состояние может повторяться). Гамильтонов путь по различным состояниям
оценивает маршрут снизу, только если матрица метрическая или повторов нет.
Контрпример «звезда»: хаб ↔ лист = 1, лист ↔ лист = 100; маршрут
`L1 H L2 H L3` стоит 4, любой гамильтонов путь по `{H, L1, L2, L3}` — ≥ 102.
Исправление: BHK по метрическому замыканию на индуцированном подграфе
состояний (маршрут не может пройти через состояние вне множества). Между
соседними «первыми посещениями» маршрут платит не меньше кратчайшего пути →
оценка валидна на любой матрице; на метрической матрице замыкание —
тождество. В продакшн-отсечениях BHK не используется с 2026-07 (KI-S3),
поэтому это дефект публичного контракта, а не текущих результатов LBBD.

### A-07…A-09, A-13

* **A-07:** `stamp_honest_coverage` считал строки, а не различные операции:
  `[op1, op1]` на задаче из двух операций получал `FULL`.
* **A-08:** `CoveragePaceController.observe_window` вызывался только на
  greedy-fallback окнах; медленные, но успешные окна внутреннего солвера —
  ровно то, ради чего существует guard, — были невидимы. Метаданные:
  `coverage_pace_windows_observed`.
* **A-09:** EMA времени ремонта ALNS усредняла кумулятивные суммы
  (смещение растёт с номером итерации) вместо поитерационных значений.
* **A-13:** оба генератора (`synaps/benchmarks/instance_generator.py`,
  `synaps/solvers/instance_generator.py`) брали `uuid4()`. ID теперь из
  отдельного детерминированного потока (`synaps/_ids.py`); поток структурного
  ГСЧ не тронут, поэтому длительности / допустимость / переналадки для того
  же `seed` совпадают с прежними (тест `test_a13_id_stream_leaves_structural_draws_unchanged`).

### A-11 / A-12. Семантика иерархической цели CP-SAT (не изменялась)

В иерархическом режиме вес `makespan` не участвует (makespan доминирует по
построению), а material / energy входят в милли-единицах
(`material_loss_scale = energy_kwh_scale = 1000`), т.е. вес 1 на material
весит в 1000 раз больше, чем в `scalarize()`. Изменение сломало бы
сопоставимость опубликованных результатов, поэтому семантика
задокументирована, а не изменена.

## 4. Архитектура: декомпозиция god-функций

Шаблон один для всех солверов: тонкий `solve()` → объект-«движок» одного
запуска (`_RhcRun`, `_AlnsRun`, `_LbbdRun`, `_LbbdHdRun`, `_BeamRun`) с явным
состоянием и короткими методами фаз; конфигурация — типизированные frozen
dataclass (`RhcRunConfig`, `_alns_config.py`) с `from_kwargs`,
воспроизводящим исторические умолчания и клампы. Штамп
`stamp_honest_coverage` — на границе `solve()` (контракт проверяется
AST-тестом). Общая бухгалтерия LBBD (`cut_kind_lb_contribution`) вынесена в
`_lbbd_cuts.py`.

| Точка входа | Было, строк | Стало, строк | Движок |
| --- | ---: | ---: | --- |
| `RhcSolver.solve` | 2 659 | 3 | `_RhcRun` + `RhcRunConfig` |
| `AlnsSolver._solve_core` | 1 577 | 3 | `_AlnsRun` |
| `LbbdHdSolver.solve` | 437 | 2 | `_LbbdHdRun` |
| `CpSatSolver.solve` | 436 | 57 | `_build_model`, `_add_resources`, `_warm_start_assignments`, `_extract_build_solution` |

Оставшиеся длинные функции — построители моделей и операторы

`_add_machine_order_and_adjacency` 240, …) — внесены в план с процедурой
golden-контроля.

## 7. Red Team итогового состояния

* **R-01.** В эксперименте 1 evidence strict-parallel под нагрузкой дал 2
  различных расписания при `det_violated = false` — выглядело как
  опровержение заявления. Разбор: стены 12.17 / 12.2 с при потолке 12 с, т.е.
  поиск остановила стена; эксперимент шёл до исправления детектора
  `_wall_cap_ended_search`. Notes дополнены; ни один прогон, остановленный
  детерминированным стопом, второго расписания не дал.
* **R-02.** Strict-режим CP-SAT ставит стену в 2× бюджета, чтобы стоп был
  детерминированным (ADR-0001, N1). Измерено (тот же evidence-файл): 6.7–12.2 с
  при бюджете 6 с. Это осознанный компромисс; кому нужна жёсткая стена —
  `determinism="fast"`. Guard `test_guard_d3_timebox_within_tolerance`
  (запас 1.5×) пограничен: после переезда контейнера на другой CPU strict
  CP-SAT на `medium_stress_20x4` при бюджете 6 с тратил 8.89 / 9.62 / 9.72 с в
  исходном коде и 8.85 / 9.66 / 9.80 с в текущем (детерминированное время
  3.0 и makespan 184 в обоих) — то есть 1.48–1.63×, guard краснеет в обоих
  деревьях. Регрессии нет; отношение «детерминированная единица → секунды»
  зависит от CPU.
* **R-03.** LBBD / LBBD-HD создают `ProcessPoolExecutor` с методом `fork` из
  процесса, где уже работают потоки OR-Tools / NumPy (DeprecationWarning
  Python 3.12; в Python 3.14 метод по умолчанию на Linux — `forkserver`).
  Риск дедлока в дочернем процессе. Переход на `forkserver`/`spawn` меняет
  стоимость старта пула на каждой итерации — нужен замер; вынесено в план.
* **R-04.** `int(time_limit_s)` в LBBD / LBBD-HD — консервативно (бюджет
  недоиспользуется, но не превышается); оставлено.
* **R-05.** Тёплый старт LBBD-HD глотал любое исключение; теперь тип
  исключения пишется в `warm_start_error`.
* **R-06.** Golden-кейс `lbbd5hd_600` проходил только ветку
  `sub_unproven_failure` — рефакторинг допустимой ветки им не проверялся.
  Добавлены кейсы с допустимыми подзадачами; в харнесс — `lbbd_hd_stress`.
* **R-07.** Тесты с wall-clock бюджетом (`test_alns_honors_time_limit`,
  `test_guard_d3_timebox_within_tolerance`,
  `test_industrial_seed42_zero_precedence_violations` с `time_limit_s=45`)
  краснеют при параллельной нагрузке (`pytest -n 4`) и проходят на
  простаивающей машине (последний — 44 с); это свойство тестов, а не
  регрессия. Рекомендация: помечать такие тесты отдельным маркером и
  запускать в CI без `xdist`.
* **R-08.** Таблица LOC в `03_SOLVER_PORTFOLIO.md` пересчитана.
* **R-09. Паритет конфигурации.** AST-сравнение всех `kwargs.get(ключ,
  умолчание)` и обрамляющих клампов в исходных `RhcSolver.solve` /
  `AlnsSolver._solve_core` против `RhcRunConfig` / `_alns_config.py`: 79 / 79
  ключей RHC и 57 / 58 ключей ALNS (отсутствует `min_iterations` — и в
  оригинале это был no-op `_ = kwargs.get(...)`, ключ по-прежнему
  принимается). Умолчания совпали; единственное отличие — порядок `min`/`max`
  в двух клампах, различимый только на NaN; теперь NaN единообразно
  отображается в нижнюю границу (тест `test_r09_*`).
* **R-10. SIGILL нативного модуля на другом CPU — воспроизведено.** После
  паузы сессии контейнер переехал на другой хост, и уже установленный
  `synaps_native`, собранный ранее с `-C target-cpu=native`, стал падать при
  импорте: `Fatal Python error: Illegal instruction` (код 132). Python-fallback
  в `synaps/accelerators.py` такой отказ перехватить не может — процесс
  умирает. Падали и закэшированные build-скрипты зависимостей (cargo exit
  101 до `cargo clean`). Релизный job `build-native-wheels` собирает колёса из
  корня репозитория, т.е. с тем же конфигом: опубликованное колесо получило бы
  ISA раннера. Исправление — `RUSTFLAGS` (приоритет выше `rustflags` из
  конфига) с переносимой базой `x86-64-v2` / `apple-m1`; локальные сборки
  разработчика остаются `native`. Проверка приоритета: `objdump -d` по `.so`
  из `native`-сборки — 2 503 строк с `ymm` и 658 с `zmm` (AVX / AVX-512); из
  сборки с `RUSTFLAGS="-C target-cpu=x86-64-v2"` — 0 и 0.
* **R-11.** В том же job на `windows-latest` команда `maturin build` с
  `\`-переносами исполнялась бы в PowerShell; добавлен `shell: bash`.
* **Кейс `hd_medium_lb`** (LBBD-HD + local branching на `medium_20x10`)
  ограничен wall-clock: исходный код упирается и в 120-, и в 900-секундный
  лимит. При 120 с расписание и целевая функция совпали с исходным кодом,
  метаданные (итерационная телеметрия) — нет, как и ожидается для поиска,
  остановленного таймером; совпали и состав пула отсечений (3 ×
  `local_branching`, 2 дубликата отброшены, 1 пропуск по S2). Как
  свидетельство эквивалентности кейс не засчитывается; допустимая ветка
  покрыта идентичными `hd_stress` / `hd_tsp`, local branching — тестами
  `tests/test_lbbd_hd_solver.py`.
